# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

npm workspaces monorepo with two parts: `extension/` (Chrome MV3 frontend, WXT + TypeScript) and `api/` (Hono backend that owns translation, deployed as a single Supabase Edge Function), plus `shared/contract.ts` for the wire types both import. The user selects text in an input, textarea, or contenteditable field. A floating icon appears; clicking it opens a menu of favorite languages, and picking one replaces the selection with the translation fetched from the API.

**The extension is frontend only**: detect the selection, show the icon and menu, call `POST /translate`, and apply the result. It has no provider abstraction, provider choice, or provider config. Translation and provider selection live in the API (`api/src/resources/aiClient/requests/translate.ts`), because a provider key shipped in the extension is public.

## Commands

Root commands fan out to both workspaces (`npm test`, `npm run compile`, `npm run build`); `-w extension` / `-w api` targets one.

- `npm run db` (root): `supabase start` — local Postgres + edge runtime, needs Docker. Everything else assumes it is running.
- `npm run dev` (root): API + extension dev browser + playground together
- `npm run dev:playground -w extension`: extension + `playground/` on http://127.0.0.1:5555 (opened via `webExt.startUrls` in `extension/wxt.config.ts`); the manual test environment
- `npm run dev:api` (root): the **local Node server** on http://127.0.0.1:8787/functions/v1/, `node --watch`. Needs no Docker; env comes from Node's `--env-file-if-exists` (root `.env` then `supabase/functions/.env`), so there is no dotenv import-order rule.
- `npm run dev:api:edge` (root): `supabase functions serve` on http://127.0.0.1:54321/functions/v1/ — the real gateway and the real Deno runtime. **Run this before deploying**; it is the only local path that exercises them.
- `npm run token -w api`: mints a signed dev token for curl, so the Node server can be used with no Supabase stack running. Takes an optional user uuid. Deno runs the TS directly — no build step, so keep API code erasable: no enums, no parameter properties.
- `npx supabase migration new <name>`, then `npx supabase migration up` (local) / `npx supabase db push` (linked project). Files live in `supabase/migrations/`; don't edit applied ones.
- Deploy the API: `npx supabase link --project-ref <ref>`, `npx supabase secrets set --env-file supabase/functions/.env`, `npx supabase functions deploy api`.
- `npm run build`: production build into `extension/output/chrome-mv3`. Load it unpacked from `chrome://extensions`.
- `npm run compile`: type check. The extension needs the generated `.wxt/` types; run `npx wxt prepare` in `extension/` on a fresh checkout or after adding entrypoints.
- `npm test`: all unit tests (Vitest), both workspaces
- `npm run deploy`: compile + test + zip + `wxt submit` to the Chrome Web Store. Credentials live in the git-ignored `.env.submit`, created by `npx wxt submit init`. Bump `package.json` version first, because the manifest version comes from it. `npm run deploy:check` is a dry run.
- Single test file: `npx vitest run src/api.test.ts` from inside `extension/` or `api/`. Single test by name: `npx vitest run -t "surfaces the API error message"`.

There is no linter configured. `playground/index.html` has one of each field type.

## Architecture

`srcDir` is `src`, so WXT entrypoints live in `src/entrypoints/` (`background.ts`, `content.ts`, `options/`). Import WXT APIs explicitly from subpaths (`wxt/browser`, `wxt/utils/storage`, `wxt/utils/define-background`, …) instead of relying on auto-imports.

Extension layout:
- `src/api.ts` has `translate()` and `detect()`, the only `fetch`es to the API. The base URL comes from `WXT_API_URL`, falling back to `http://127.0.0.1:54321/functions/v1/api`, and its origin must be in `host_permissions` (`wxt.config.ts` lists the local stack and `https://<project-ref>.supabase.co`; keep the two in sync by hand). API error bodies become a plain `Error` carrying the API's message.
- `src/entrypoints/background.ts` handles messages and calls `translate()`. The page url is read from the `onMessage` `sender`, not the message body, so a compromised page can't forge it — that is why `handle()` takes the sender.
- `src/settings/` is a **cache**, not the source of truth: settings live on `profiles.settings` so they follow the user across devices. The content script reads the cache on every icon click (fast, works offline and signed-out); the options page and the sign-in handler go through the worker's `get-settings` / `save-settings`, which write the cache after the API answers. Saves are API first, cache second, so the server stays authoritative. Last write wins. An empty `favoriteLanguages` (the shared default) means "not chosen yet": `storageSettings.get()` fills it with `browserLanguages()` (`navigator.languages` → supported base codes, `en-US` → `en`; first = default target), since the server can't see the browser.
- `src/auth/` is the session and OAuth flow. `session.ts` is a **separate** storage item from `Settings`, because the options page's `update()` does a shallow spread that would clobber a nested session.
- `src/core/languages.ts` is the static language list.

**API** (`api/`): deployed as two Supabase Edge Functions (`api`, `health`); run locally as a Node server. It is layered — entrypoint → wiring (`app.ts`) → middleware → controller → AI request / repository → resource (`resources/db.ts`, `resources/aiClient/client.ts`), each layer calling only the one below it. **[`.claude/rules/api-architecture.md`](.claude/rules/api-architecture.md) is the source of truth for that split** (what each layer owns, what it must not do, the folder map, where new code goes); read it before adding a route, a guard, a provider call or a table. `index.ts` only calls `Deno.serve(app.fetch)`, so tests hit `app.request()` with no port. Error bodies are `{error:{message, code}}` and `src/api.ts` surfaces the message; keep the codes in sync with `shared/contract.ts`. `repositories/translations.ts` (`translationsRepository`, mapping app records to columns) saves every translation, failures included, to the Postgres table `translations` (created by `supabase/migrations/`); a row's id starts with the request's log id. A row also records `user_id` (FK to `auth.users`, `on delete set null`), `url` (the page the extension was used on), `model` (what the provider reports it used, not what was requested) and the provider's `input_tokens` / `output_tokens` / `total_tokens`; all nullable, since rows predating auth have no user, failures report no usage, and non-extension callers send no url. `trace_id` is a **generated** column (`sha256(text)` in hex, indexed), not written by the repository: it fingerprints the selected text so every attempt on it -- retries, other target languages -- groups under one id and the action can be repeated. There is **no RLS yet** — nothing reads this table from a client, and the function writes it over a connection that bypasses policies anyway.

**Every provider route runs `guardText` first** (`middleware/guard.ts` → `requests/validateGuard.ts`, a TypeSafe `choice`): text typed with the wrong keyboard layout (`ghbdtn` for `привет`) 422s with code `mistyped`, random keystrokes (`adfasdf`) with `gibberish`, before the provider call. The client re-types a mistyped text locally with `switchLayout` (`src/core/layout.ts`) — a key-position map, so the fix costs nothing and can't hallucinate. There is no override: a gibberish text gets nothing until it changes. The guard **fails open** (a TypeSafe outage lets the text through). A `/translate` that carries `sourceLang` **skips** the guard: that language came from a `/detect` that already guarded the same text, and the second call cost 0.3–0.9 s. A `/fix-grammar` with `guarded: true` skips it for the same reason: the client sends it only when a `/check` of that exact text answered. Detection, the guard and the error count use `typeSafeClient` (`TYPESAFE_API_KEY`); translate, fix-grammar and rewrite use OpenAI.

`POST /detect` answers what language a selection is in (`{lang}`, a TypeSafe `choice` over `shared/contants.ts`'s `LANGUAGES`). It is asked when the in-page menu opens, before a target is picked, together with a `/check` of the selection (the menu's "Grammar fix" item shows its error count) — each of those is a guard call plus a provider call. `repositories/detections.ts` saves each attempt to `detections`, which mirrors `translations` column for column (id, usage, error, the generated `trace_id`), so a detection and the translations of the same text join on `trace_id` without a foreign key. Its one extra column, `verified`, is **written by `POST /translate`, never by the detection**: `null` = the menu was closed without translating, `true` = the user translated with the detected language, `false` = the user sent a different `sourceLang` and the detection was wrong. Only the user's latest detection of that exact text is marked, in a `waitUntil` that can't slow or fail the translation. `verify()` matches the row by hashing the text in SQL (`::text::bytea`, not `::bytea` — a bare cast types the bind parameter as bytea and Postgres would parse the string as escaped binary instead of hashing its characters), so the client carries nothing but the language.

`POST /fix-grammar` takes the same body as `/detect` (`{text, url?}`) and returns `{text, html, edits}` with grammar, spelling and punctuation fixed in the same language — unchanged if nothing needed fixing — plus phrasing a native speaker wouldn't use. `edits` (`FixEdit`: `start`/`end` into the request text, `original`, `replacement`, `kind` `error`|`native`, a one-line `reason`) are the same list as `html`'s `span.fix`s, in order. The model returns only the edits (`original` quoted with enough context to be unique, `replacement`), never the whole text: `utils/applyEdits.ts` rebuilds the corrected text, dropping an edit whose `original` isn't found. Offsets come from the server diff (`requests/fix-grammar/utils/toEdits.ts`), never from the model, which only labels each edit's kind and reason; an edit whose either side is only whitespace (an insertion or deletion) takes in the next word, so it has something to underline and `replaceSelection`'s trim can't eat it. The extension asks it on a click (the grammar icon or the menu's "Grammar fix"), and **prefetches** it as soon as a `/check` reports errors, so the click opens the fix instead of a skeleton (one extra fix per typing pause with errors; a failed prefetch leaves the badge alone). The provider call is **streamed only to stop early**: `fixGrammar` returns at `response.output_text.done`, because `response.completed` trails it by 0.1-2 s, so the fix reports no `usage`. It runs on `service_tier: 'priority'` (measured ~1 s faster and steadier, at a higher token price). Rate limited like the other provider routes. It runs **without** `guardText`: the controller runs `validateGuard` in parallel with the fix (a verdict aborts it and 422s; a guard failure lets it through), so an unguarded call waits for the slower of the two, not both. The widget's paragraph fixes always follow their sentences' `/check`s and send `guarded: true`. `repositories/corrections.ts` saves each attempt to `corrections`, which mirrors `translations` (id, usage, error, generated `trace_id`).

`POST /check` (same body) returns `{errors}`: how many errors the text has, not what they are (`requests/grammarQuality.ts`, a TypeSafe `choice` over "0".."9", 9 = 9 or more). It runs **without** `guardText`: `grammarQuality` asks the guard's question (`verdictQuestion` from `validateGuard.ts`) in the same TypeSafe call and the controller 422s the verdict itself, one round trip instead of two. Unlike `guardText` it doesn't fail open: a failed call is a 502. It is the cheap background call behind the badge. Not saved.

`POST /rewrite` takes `{text, url?, style}` with `style` one of `REWRITE_STYLES` (`natural` = how a native speaker would say it, same register; `formal` = official/business register) and returns `{text}` rewritten in the same language, errors fixed along the way. Same guards as `/fix-grammar`. `repositories/rewrites.ts` saves each attempt to `rewrites`, which mirrors `corrections` plus a `style` column. No extension UI yet.

`POST /explain` (`{text, context, targetLang, url?}`: a highlighted word or phrase of a meeting line, at most `MAX_EXPLAIN_LENGTH`, with its line) returns `{meaning, examples, lang}` -- the meaning in `targetLang`, two examples in the highlight's own language. It is both Explain and what "Add to vocabulary" saves. `guardText` runs on `text`. `POST /summarize` (`{lines: {speaker, text}[], targetLang}`, at most `MAX_SUMMARY_LINES` / `MAX_SUMMARY_CHARS`) returns `{points}`, 3-7 key points, decisions and follow-ups; no `guardText` (a dialog isn't one typed text), and it logs the line count, not the transcript. Neither is saved to a table.

`POST /transcribe` is voice input: multipart (`audio` file part, `audio/*`, at most `MAX_AUDIO_BYTES`; optional `url`), parsed by `parseTranscribeBody` -- `validate` reads `formData()` when the content-type is multipart, JSON otherwise. The controller runs `requests/transcribe.ts` (`client.audio.transcriptions.create`, `TRANSCRIBE_MODEL` = `OPENAI_TRANSCRIBE_MODEL` ?? `gpt-4o-transcribe`) and then `detectLang` on the text, returning `{text, lang}` in one round trip (`text: ''`, `lang: 'und'` when nothing was heard), so the client sends that `lang` as `sourceLang` and the guard is skipped. No `guardText`: speech can't be mistyped. `repositories/transcriptions.ts` maps an attempt to `transcriptions` (size, mime type, text, lang, model, error -- never the audio), but saving is **switched off for now** (`SAVE_TRANSCRIPTIONS = false` in `controllers/transcribe.ts`).

**Only the API knows which AI system does the work**: a client does action → request → view and never names a provider (responses still carry `model` and `usage`, for dev). Live dictation keeps that too. `POST /voice-session` (no body; `requireUser`, `rateLimit`) returns `{ticket, expiresAt}`: a 60 s **ticket** for the live-dictation socket (`utils/voiceTicket.ts`, HMAC-SHA256 over `{sub, exp}` with `VOICE_TICKET_SECRET`; stateless, so short-lived rather than single-use), never a provider secret, never logged. The socket is the **`voice` function** (`src/voice.ts`, `Deno.upgradeWebSocket`; `…/functions/v1/voice?ticket=…`, the ticket in the query because a browser WebSocket can't send headers; `verify_jwt = false` for the same reason, so the ticket is its auth -- a bad one closes with 4401). `controllers/voiceStream.ts` relays: it opens the provider session (`requests/liveTranscribe.ts`: `voiceSession()` mints a Realtime client secret -- a `transcription` session: 24 kHz PCM, `LIVE_TRANSCRIBE_MODEL` = `OPENAI_LIVE_TRANSCRIBE_MODEL` ?? `gpt-live-transcribe`, no turn detection, the live models refuse it -- then the provider socket), buffers the client's audio until it opens, reads the provider's events with `requests/liveTranscribe/utils/liveTranscript.ts`, and answers in our own `VoiceServerEvent`s (`ready`, `text` = everything heard so far, `done {text, model}` after the client's `commit`, `error`); either side closing ends both. Locally `server.ts` takes the WebSocket upgrade on `/functions/v1/voice` with the `ws` package and sets a per-process `VOICE_TICKET_SECRET` when none is configured (one process signs and checks); the edge needs it in the function secrets, else `/voice-session` 502s and dictation falls back to `/transcribe`. The live models smooth grammar slightly ("I has send" → "I have sent"); `/transcribe` is verbatim. **Both transcription calls get `DICTATION_PROMPT`** (`requests/dictationPrompt.ts`: a person dictating a message to people, often opening with a greeting and a name, not talking to an assistant): without it a short greeting is guessed from nothing ("hey John" came back as "ChatGPT", "Agent", "平仮名" -- 1 right in 6), with it 6 in 6 on the live model. It steers context and spelling only, never rewrites words, so a real "ChatGPT" stays.

`GET /stats` (`requireUser`, no rate limit) is a **dev counter**: the words of every successful translation (`total`, `byDay`, top level as before), the seconds spent dictating (`dictationSeconds: {total, byDay}`, tenths) the words dictated (`dictationWords`, the final transcripts' words; a dictation that is then translated also counts in `total`), and those per transcription model (`dictationModels: {[model]: {dictations, seconds, words}}`, in total only), per UTC day and in total, kept by `repositories/wordStats.ts` in a JSON file (`WORD_STATS_FILE`, default `api/word-stats.json`, gitignored). The translate controller records the words in a try/catch, so it never fails a translation. `POST /stats/dictation {seconds, words?, model?}` (`parseDictationBody`: seconds > 0, ≤ `MAX_DICTATION_SECONDS`; words a whole number ≤ `MAX_DICTATION_WORDS`; model a plain id of ≤ 64 chars; the live model comes from `/voice-session` through the recorder's `live`, the upload's from `/transcribe`, none when transcribing failed) adds one recording and answers 204 even when it can't write: the recorder measures mic start to Stop (capped at its 60 s), and the worker reports it once the final transcript is known -- live or uploaded; 0 words when nothing was heard or transcribing failed -- not awaited (a cancel is not counted). The deployed edge has no writable disk, so there it counts nothing.

`profiles` is the user record we own — `auth.users` belongs to GoTrue and must not gain application columns. The `on_auth_user_created` trigger (in `supabase/migrations/`) copies id/email/provider metadata across at sign-up; `repositories/profiles.ts` upserts anyway so a missing row still yields working settings. It holds `settings` as jsonb mirroring the extension's `Settings` object 1:1, merged over `DEFAULT_SETTINGS` on read so a new setting needs no data migration. Still no RLS — the API is the only reader. The save never fails a translation.

API rules:
- **Four entrypoints, one app.** `index.ts` (edge, `Deno.serve`), `voice.ts` (edge, the live-dictation WebSocket), `dev/health.ts` (edge, public probe) and `server.ts` (local Node, which also takes the voice upgrade) are the *only* places allowed to know which runtime they are on. `app.ts` must never branch on runtime — if something differs, it belongs in an entrypoint or in `dev/dev-gateway.ts`.
- `dev/dev-gateway.ts` **emulates** the Supabase gateway locally: the `/functions/v1/...` prefixes, the gateway's own 401 bodies (`{code, message}`, not the app's `{error:{...}}`), and a real signature check standing in for `verify_jwt`. It accepts both token kinds: **ES256/RS256 via the GoTrue JWKS endpoint** (how real sessions are actually signed — the local stack does *not* use the legacy shared secret) and **HS256** for tokens from `npm run token -w api`. **Dev-only auth bypass:** a request with *no* `Authorization` header is signed in as `DEV_USER_ID` (default `00000000-0000-4000-8000-000000000000`, seeded into `auth.users` by `supabase/seed.sql` on `db reset`), so the extension works signed out against the Node server; a token that *is* sent is still verified. `dev:api:edge` and production stay gated. It is an emulation and can drift — that is why `npm run dev:api:edge` before deploying is a rule, not a suggestion.
- `api/src/**` deliberately stays outside `supabase/functions/`. `[functions.api]` / `[functions.health]` in `supabase/config.toml` point `entrypoint`/`import_map` at it (paths resolve from `supabase/`), which keeps the npm workspace layout for vitest and `tsc`. Don't move the sources. `api/dev/` holds local-only code (`dev-gateway.ts`, `dev-jwt.ts`, `dev-token.ts`), never deployed, plus `health.ts`, the one deployed file there: `[functions.health]` points at `../api/dev/health.ts`.
- `app` is built with `basePath('/api')` because Supabase strips `/functions/v1` and hands the app paths starting with the function name. The basePath and the function name must match; tests request `/api/translate`.
- Read config through `env()` in `env.ts` (Deno.env when deployed, `process.env` under vitest), never `process.env` directly. Supabase has secrets at module load, so module-level reads are fine.
- The DB save is wrapped in `waitUntil()` (`EdgeRuntime.waitUntil`), which keeps the isolate alive until the insert lands. Without it the row is lost the moment the response returns. It is a no-op under vitest.
- Runtime deps are declared in `api/deno.json` (Edge Functions have no `package.json` support); the same packages sit in `api/package.json` `devDependencies` only so vitest and `tsc` resolve them. Bump both together.
- Secrets live in git-ignored `supabase/functions/.env` (template: `.env.example` beside it), loaded by `supabase start` / `--env-file` and pushed with `supabase secrets set --env-file`.
- **Two functions, because `verify_jwt` is per-function and the gateway enforces it before the handler runs.** `api` has `verify_jwt = true` (signed-in users only); `health` has `verify_jwt = false` so uptime probes stay anonymous. That is the only reason `health.ts` is a separate entrypoint rather than a route on `app.ts`.
- `userIdFrom()` in `middleware/auth.ts` **decodes but does not verify** the JWT — the gateway already checked the signature and rejects the publishable key. Setting `verify_jwt = false` without adding signature verification would make `sub` forgeable. The two are coupled; the comment at the call site says so.
- A 401 can come from the gateway *before* the handler, with a different body (`{code, message}`, no `error` wrapper). `extension/src/api.ts` therefore derives `unauthenticated` from the **status**, not the body, or a signed-out user gets a generic error instead of the sign-in prompt.
- OAuth is hand-rolled PKCE in `extension/src/auth/oauth.ts` (`chrome.identity.launchWebAuthFlow` + two fetches), so the extension still has zero runtime dependencies. `apikey` goes in the **query string** on `/auth/v1/authorize` because a navigation carries no headers. Tokens refresh **on demand, never on a timer** — an MV3 worker is killed between requests.
- Adding an OAuth provider = a `[auth.external.<name>]` block in `supabase/config.toml` plus an entry in `extension/src/auth/providers.ts`. Nothing else.
- Two env files: git-ignored **`.env` at the repo root** holds provider ids/secrets that the CLI substitutes into `config.toml` at `supabase start`; **`supabase/functions/.env`** holds function runtime secrets. Don't merge them.
- No `DATABASE_URL` in production — Supabase injects `SUPABASE_DB_URL`; `resources/db.ts` prefers `DATABASE_URL` as an override. postgres.js runs `max: 1, prepare: false` because each isolate gets its own pool.
- `app.test.ts` and `dev/dev-gateway.test.ts` mock the AI requests (`resources/aiClient/requests/*`, `validateGuard` and `grammarQuality` included), `resources/db.ts` and the repositories, so API tests need no key, DB or network. Mock any new module that opens a connection when it loads — `resources/aiClient/client.ts` throws without `OPENAI_API_KEY`, so a stale mock path fails the whole file on load.
- `GET /health` returns 503 only when a DB URL is set and `select 1` fails (5 s connect timeout); `db: "disabled"` is still 200.

**UI layout**: `entrypoints/` only mounts. `components/` holds the reusable presentational pieces (buttons, icons, inputs, typography, menu, list, `CountBadge`, `theme.css`); `widgets/translator/` is the in-page widget; `popups/toolbar/` and `popups/settings/` (mounted by the `options` entrypoint) are the extension's own pages. [`.claude/rules/extension-ui.md`](.claude/rules/extension-ui.md) says what each may import.

**Runtime flow**: The content script and the options page talk to the background worker only through the typed protocol in `src/messaging/messages.ts` (`translate`, `detect`, `explain`, `summarize`, `open-options`, `sign-in`, `sign-out`, `get-account`, `get-settings`, `save-settings`, `voice-start` / `voice-stop` / `voice-cancel`). Sign-in must run in the worker: `chrome.identity` is unavailable to content scripts and the options page. Responses are `{ ok, data } | { ok: false, error }`, because `Error` objects don't survive messaging. When adding a message type, update both `Message` and `ResponseMap`. The API call must stay in the background worker: `host_permissions` exempt it from page CORS, and on HTTPS pages a content-script fetch to an `http://` API would be blocked as mixed content.

**Voice input** (popup and widget alike). One pipeline; the surfaces differ only in where the result lands.
- **Recording**: one **offscreen document** (`entrypoints/offscreen/`, the `offscreen` permission) holds the mic for every surface, driven by the worker over `messaging/recorder.ts` (`target: 'offscreen'`; every runtime message reaches every extension page, so it filters on that). Not the worker (no `getUserMedia`), not a content script (each site would ask for the mic). Its messages run one at a time, so a Stop pressed while a cold mic is starting still finds the recording. It records the file (MediaRecorder, the fallback) and taps 24 kHz PCM for the live session (`core/pcm.ts`; a `ScriptProcessorNode`). It stops itself at 60 s, and after **3 s of silence** (`SILENCE_LEVEL` / `SILENCE_MS`, from the start or the last sound) it flags `silent`, on which both surfaces stop as if Stop was pressed (`stop` ignores repeats).
- **Permission**: an offscreen document can't prompt. Without a grant `getUserMedia` rejects, the worker opens `options.html#mic` (the "Microphone" card, `useMicPermission`) and answers error code `mic-blocked`.
- **Live text**: right after `start` the worker asks `POST /voice-session` (not awaited) and hands the recorder the socket url with its ticket (`live`, `voiceSocketUrl` in `api.ts`: the API base with `/api` → `/voice`, http → ws). The recorder opens the API's live-dictation socket, flushes the PCM buffered meanwhile and streams the rest as `{type:'audio'}` frames; `text` events are the live text. It never talks to a provider (see `POST /voice-session` above).
- **While recording**, every 100 ms the recorder sends `voice-level` (`{level 0..1, ms, text?, silent?}`): the popup, an extension page, hears it directly; a tab gets it from the worker, forwarded to the `owner` frame the recorder echoes back (the worker keeps no state). `components/Recording.tsx` draws five bars, an m:ss timer and all of the live text (scrolling past ~8 lines, newest words in view via a `flex-col-reverse` box). Both surfaces also feed the live text to `core/liveLanguage.ts` (one `/detect` once it has 4 words, one request at a time) and, once that says `en`, to `core/sentenceFixes.ts`, which sends each **ended sentence** to `/fix-grammar` on its own (2 in flight, each text once). The unended last sentence is never asked early: the live text lags the speech, so the final transcript rewords it.
- **Stop**: the recorder sends `commit` and waits ≤3 s for `done` (its text and model); `voice-stop` returns `{text, lang}`, asking `/detect` only when the UI didn't send the language (`voice-stop {lang}`). Any live failure (ticket, socket, an `error` event, a close before `done`, timeout) silently falls back to the file: the worker posts it to `/transcribe` as multipart (`call()` in `api.ts` passes a `FormData` through; runtime messages are JSON, so the audio travels as a data: url). With the language already known, nothing reads as a loader: the widget opens its result at once on the live text (`openDictation`) and swaps in the final transcript (`edited` + `dictated`) before asking anything; the popup puts the live text in the input (`previewDictation`, state `finishing`). Otherwise "Transcribing…" shows until the text and its language are back.
- **Result**, by language: **English** gets the grammar panel on the transcript, its fix being `sentenceFixes.finish(final)` (the unchanged sentences reused, the rest asked, `mergeFixes` making one fix of the whole text; a guard verdict on a sentence counts as clean). A language the user has a pair for (`pairFor(topPairs(history, Infinity), lang)`, the menu's `pairTarget` rule) is **translated into that target at once**. Anything else gets the favorites (the widget's menu, the popup's "into" picker, whose pick translates).
- **Stats**: after `voice-stop` the worker reports `{seconds, words, model}` to `POST /stats/dictation`, not awaited (see `GET /stats` above).
- Shared pieces: `components/GrammarPanel.tsx` (`GrammarView`), `components/Recording.tsx`; `core/fixEdits.ts` (`applyEdits`, `withoutFixEdit`, `Chunk`, `cleanFix`, `isFinished`, `mergeFixes`, `escapeHtml`; `widgets/translator/chunks.ts` re-exports the latter for the field flow). History entries made from a dictation carry `voice: true`.

**Meeting mode** (`src/widgets/meeting/`): only the **transcript** is still a demo -- `hooks/demoFeed.ts` plays a scripted conversation (live text word by word, then a committed line) in place of the meeting audio pipeline; every action on it calls the real API. One result card per line. `transcriptActions(deps)` turns the buttons into requests; each surface passes `messaging/transcriptSenders.ts` (the worker messages + vocabulary + the target language) and its dispatch. `widgets/meeting/state.ts` (pause, minimize, end, rename, plus the transcript state) and `view.ts` are pure and tested; `MeetingPanel.tsx` is presentational. Speaker names are not stored between meetings.

**Toolbar popup** (`src/popups/toolbar/`, mounted by `src/entrypoints/popup/main.tsx`): the toolbar icon opens it (WXT adds `default_popup`; the old `action.onClicked` → options page is gone, settings are the popup's sliders icon). `ToolbarPopup.tsx` is the container; its logic is in `hooks/` (`useTranslation`, `useHistory`, `useActiveSite`, `usePinned`) and the presentational screens in `screens/` (Home, Languages picker, History; stories beside each). The text card has a mic (`hooks/useDictation.ts`: listening / transcribing card, ↵ stops, `pagehide` releases the mic); dictated English opens the `GrammarPanel` under the input (`hooks/useGrammarFix.ts`: Replace / ↵ splices the input's text, Replace all / ⌘↵ outside the textarea, Ignore; applied edits go to history as `kind: 'grammar'`; typing hides a stale fix). It translates typed text through the same `detect` / `translate` messages (debounced detect; "Try another" re-asks and keeps versions in memory only). The popup tracks no site: the worker sends `url` only from `sender.tab` (the popup and options page have none), and popup history entries have an empty `site`. History is **local only**: `settings/history.ts` (`historyStore`, key `local:popupHistory` kept from when it was popup-only; the last 200 entries; no age-based pruning, by choice). It takes popup translations, in-page widget translations (recorded by `useTranslatorFlow` once applied or shown) and **applied** grammar fixes and rewrites (`kind: 'grammar'`, on Replace or Copy, never for background checks; a run of Replaces is **one** entry, original → final, rewritten in place by its `at` (`withEntry` replaces a same-`at` entry); the user's typing or undo in between is an intermediate change that doesn't end it. The widget's run (`rememberFix`) is per field and ends when the field is emptied (a chat's send) or another field is fixed; a selection's run ends on any change of its text. The popup's ends when the input is emptied, a dictation arrives or an entry is restored (`endRun`)); no `kind` = a translation. `voice: true` marks an entry whose text was dictated (the widget's `remember` sets it while `State.dictation` is open; the popup for its dictated text's translation and grammar fix), shown as a small mic to the right of the entry's icon. Each card and the Recent row start with a translate / grammar icon; a grammar entry's chip reads "Grammar", it never offers "Translate this again", and opening it puts the fixed text into the input. "Used lately" (per side: sources in the from-picker, targets in the into-picker), the History filter tabs (`topPairs`) and the day groups (`byDay`) derive from it. The Home pair defaults to `defaultPair` (the most used history pair, else the first two favorites); detection `orient`s it (typing the target language flips it, any other language becomes the source), and only a picked or detected source is sent as `sourceLang`. Once history has two pairs they show as chips above the selects. **Pinned languages**: the picker's rows (Yours, search results, A–Z) carry a pin toggle (`pin` icon, shown on hover, filled + accent when pinned; `Row`'s `action` slot, since a button can't nest in a button). Pins live in `settings/pinned.ts` (`pinnedLanguages`, key `local:pinnedLanguages`) — **chrome.storage.local only, not the synced `Settings`**, by choice — because the default favorites come from the browser's languages and the user needs a way to keep their own on top. `intoLanguages(favorites, history, pinned)` puts every pin first, then the most used other favorites up to 3 in all; the from side is `pinFirst(pinned, favorites)`. The in-page menu reads the same pins in `openMenu`. A star toggle is stored on the entry (`starred`, the History "Starred" filter) and never sent: there is no feedback endpoint. Delete / Clear all keep the previous list in memory for a single footer Undo, dropped on leaving History. Every translation card has "Translate this again" beside Copy, which opens the entry on Home and appends a new version. The header switch edits `Settings.disabledSites` for the active tab's host (`activeTab` permission gives the popup its url). **Insert** goes popup → `tabs.sendMessage(tabId, {type:'insert'})` → the content script's `insertIntoFocusedField` (`content/insert.ts`, caret or selection of the page's focused field, then `replaceSelection`). It is not a worker message, and only the frame holding the field answers, so an undefined answer means "no field focused".

**Content script** (`src/entrypoints/content.ts` + `src/content/` for the DOM work + `src/widgets/translator/` for the widget):
- `selection.ts` snapshots the selection when the icon appears: offsets for text controls, a cloned `Range` for contenteditable. Before replacing, it checks with `isSelectionUnchanged` that the text wasn't edited during translation. Only `text`/`search` inputs and textareas count, and `isTextControl` also drops login/contact/payment inputs via `isExcludedField` (autocomplete tokens, `inputmode`, `spellcheck="false"`, and `name`/`id`/`aria-label` matching login/user/email/otp/card/phone…; name rules apply to `<input>` only, since a textarea is prose). A page opts out with `data-ai-translator="off"` (Grammarly's `data-gramm="false"` is deliberately ignored: ChatGPT and claude.ai set it on their composers) on the field or any ancestor, contenteditable and page text included.
- **Turned-off fields**: hovering a field's icon (corner or in-field selection, never page text) opens a pill with "Turn off in this field". It stores `{site, key: fieldKey(el), label}` in `settings/disabled-fields.ts` — **chrome.storage.local only, deliberately not in the synced `Settings`**. `fieldKey` prefers `data-tid`/`name`/`aria-label`/`placeholder` and strips uuid/digit runs from ids, so Teams' per-load `new-message-<uuid>` still matches. `useSiteGate` mirrors it in an `offFields` ref (same pattern as `siteDisabled`); the options page lists them with "Turn back on".
- **Disabled sites**: `Settings.disabledSites` (hostnames, validated by `HOSTNAME` in `shared/contract.ts`) turns the whole widget off on a site and its subdomains (`isSiteDisabled` in `core/sites.ts`). `useSiteGate` keeps it in a ref fed by `storageSettings.watch`, so an options-page save applies to open tabs without a reload. The options page takes one hostname per line; `parseSites` reduces pasted urls to hostnames. `PUT /settings` replaces the whole jsonb, so every save sends the full `Settings`.
- `replace.ts`, for contenteditable: first dispatches a synthetic `paste` event. Model-based editors (CKEditor, Lexical, ProseMirror; e.g. Teams) revert direct DOM edits, `execCommand` included, but they handle paste and cancel it, and a cancelled paste means done. Otherwise, and for inputs and textareas, it uses `document.execCommand('insertText')`, which preserves native undo and is picked up by React-style frameworks. It falls back to `setRangeText` or `Range` edits plus a synthetic `input` event. If `execCommand` returns true, trust it; don't re-apply the edit.
- **Mentions and links** (Jira/Teams `@user` chips, any `contenteditable=false` island, any `a[href]`, kept verbatim so a fix touches only prose): the contenteditable snapshot's `text` carries them as `{{1}}`, `{{2}}` tokens with the original elements in `atoms` (`serialize` in `selection.ts`, which widens a range that cuts a chip). The prompts keep the tokens, and `replace.ts` pastes `text/html` with cloned chips (then `insertHTML`, then DOM). Panels and history show the chip text via `plainText`.
- `entrypoints/content.ts` calls `mountTranslator()` and answers the popup's tab messages (`insert`, `start-meeting` → `mountMeeting()`). `widgets/translator/mount.ts` builds the **closed** shadow root on a fixed-position host (appended to `<html>`, or into the field's popup — `dialog`, `[popover]`, `[role=dialog]`, `[aria-modal]` — so the popup's outside-click dismissal and a modal dialog's inert/top layer leave it alone; a `translate` cancels a transformed popup's containing block) and renders `Translator.tsx`, a thin container: `hooks/useTranslatorFlow.ts` owns the whole flow (detect, translate, sign-in, layout fix), `hooks/usePageEvents.ts` the document listeners, `hooks/useSiteGate.ts` the disabled site/fields, `hooks/requestSlot.ts` the one-in-flight check / fix. Its state is the pure reducer in `state.ts`; `view.ts` maps state to the `WidgetView` (pure, tested); `TranslatorWidget.tsx` + `Trigger.tsx` + `panels/` are presentational only (what Storybook renders); `position.ts` is the placement math. `preventDefault` on `mousedown` inside the widget keeps focus and the selection in the page's field, so don't remove it; the one exception is the widget's own `<input type="text">` (the exception form), which needs the click to take focus. The host also stops `keydown` / `keyup` / `keypress` from bubbling past it, so typing in the widget never reaches the page's shortcuts (Gmail, Teams); `onKeyDown` (window capture) still runs first and ignores everything but Esc on the `exception` screen, so digits typed there don't pick a language.
- Two flows share the widget. A selection gets the icon above it → language menu → translate. A focused field with nothing selected gets an icon in its bottom-right corner (`getFocusedField` / `wholeField` in `selection.ts`, a snapshot of the whole field) → `fix-grammar` → the grammar panel, whose Replace / N / O rewrite the whole field. The field is re-read from its element at click time, not from focus: pressing a HeroUI button moves focus into the widget, which is also why `focusout` ignores `relatedTarget === host`.
- A third flow covers page text outside any field: `getPageSelection` in `selection.ts` returns `kind: 'page'` (tried after `getEditableSelection`, before the focused field). It gets the same icon → menu with detection, but translate only (`readOnly` hides Grammar fix and the layout item, and no `fix-grammar` is asked). The translation fills the menu's translation field (Copy), because page text is never replaced. `replaceSelection` takes `WritableSelection`, so the compiler keeps page selections out of it.
- **Multi-line fields: sentences are checked, only paragraphs with errors are fixed.** `splitChunks` (`widgets/translator/chunks.ts`) cuts the field at newlines (a paragraph over 600 chars into sentence groups; pieces under 3 words are never asked) and `splitSentences` cuts each paragraph into sentences (one under 3 words joins a neighbour, unless it is the unended last one). Two `chunkRequests` pools (`hooks/chunkRequests.ts`: each text asked once, cached per field, 100 max; 2 in flight per pool; `keep` cancels text edited away) run the round in `useTranslatorFlow`. The round is **throttled, not debounced** (`scheduleCheck`): every 300 ms while the user types, and it only asks sentences that just ended, so each sentence gets the cheap `/check` (guard + count, TypeSafe) within ~300 ms of its full stop. The sentence being typed (`isBeingTyped`: caret inside it -- an edit in the middle of a sentence, ended or not -- or after it with only whitespace between and not ended; a caret right after a full stop is a sentence just finished; a short unended last piece stays apart, so "My" doesn't hold back the sentence before it) waits until it ends, or until a debounced pause (1 s more with no input) or a click sets `finished`. As soon as a paragraph's checked sentences sum above 0, `/fix-grammar` gets (with `guarded: true`) the whole paragraph once all of it is checked, else, while the user types on at the paragraph's end, its **ended part** (paragraph start to the last ended sentence; `toFix`; not for an edit in the middle, where the earlier fix carries over) -- so underlines appear while the user types on, and the whole paragraph's later fix carries them over meanwhile. An edit does **not** cancel that paragraph's fix in flight (`keep(…, finish)`): its input is billed already and its output is ~100 tokens, so it answers into the cache, without holding a slot, and serves an undo. Until the edited paragraph's own fix answers, `carryOver` underlines it with the newest earlier version's edits that still apply: the common start and end of the two texts (widened to whole words only where the change touches a word) are unchanged, edits there are kept or shifted, edits in the changed region dropped; none when under half the earlier version survived. A paragraph whose checks all say 0 is **never sent to OpenAI** (`cleanFix`); a check that misses an error is trusted. `fieldStatus` turns the caches into one whole-field check: the badge is the checks' sum (a fixed paragraph counts its edits), the underlines and panel the `mergeFixes` of the fixed paragraphs, so the badge, underlines and panel code are unchanged. An edit re-asks only its sentence (and its paragraph's fix); undo asks nothing. A check that is answered but unknown to the caches (`settled`: an applied fix or a Replace's rebase) is left alone. Any piece's guard verdict is the field's. ponytail: `serialize` emits no newline between contenteditable blocks, so a contenteditable is one paragraph. The `/check` description below covers selections and the menu too.
- The focused-field icon is pre-checked: focusing a field, and each `input` or `beforeinput` (debounced 500 ms; CKEditor/ProseMirror/Lexical cancel `beforeinput` and never fire `input`), runs `check` (`POST /check`, the error count only) in the background. While in flight the icon shows a centered spinner (`isChecking()`), then the count (orange) or a green check (`badge()`, only while the checked text still matches the field). **An open panel follows later fixes**: while `loading` (clicked, hovered or dictated), each answer swaps in the latest fix and keeps the edit the user was reading (`followEdit` in `state.ts`: the same `original→replacement` nearest its old start, else the nearest edit); a hover panel whose edit vanished goes back to the icon, since it sits on that underline. While loading, the header's change count is a skeleton. Clicking opens the grammar panel (`panels/GrammarPanel.tsx`, one edit at a time: the fixed text with the shown edit picked out, then its kind, `original → replacement`, reason, ‹ › (or ← / →, which leave the caret alone; in the popup not while the textarea is focused) with "i of N", and Replace ↵ / Ignore / Replace all · N ⌘↵ (Ctrl ↵ too); no Copy, no rewrite — `/rewrite` has no widget UI). **↻ Re-check this sentence** (beside ‹ ›, widget and popup alike): the user doesn't trust the shown edit, so its sentence (`sentenceAt` in `core/fixEdits.ts`, `Intl.Segmenter`, widened when the edit crosses a sentence end) is sent to `/fix-grammar` alone, past every cache (`guarded: true`: the panel's text passed the guard), and its edits replace only that sentence's (`spliceFix`, which rebuilds `text` / `html` the API's way). On a multi-line field the paragraph's cached fix takes the same splice (`chunkRequests.set`), so the next round keeps it; screen flag `rechecking` (a spinner in place of ↻), separate from `loading` so `publish` doesn't treat the panel as waiting as a skeleton and asks `fix-grammar` (`loadFix`, its own `pendingFix`), reusing a fix already fetched for the same text; the fix's own `span.fix` count then replaces the badge's. Typing while the panel is open closes it. **Inline underlines**: while the corner icon (or a hover-opened panel) is up on a textarea or contenteditable — never a single-line `<input>` — and the prefetched fix still matches the field's text, each of its `edits` is underlined (`hooks/useUnderlines.ts`, `panels/Underlines.tsx`): red for `error`, blue for `native`. Text-control rects come from one mirror (`textControlRects` in `selection.ts`), contenteditable ones from `rangeAt` (the serialized offsets back to a DOM range, a mention counting as its `{{n}}` token). Hovering one 300 ms opens the same panel on that edit (`hover: true`, under the underline's first line; `loading` while paragraphs are still being fixed); 200 ms off both the mark and the panel closes it, and ↵ counts only while the pointer is on it. Replace writes only the shown edit (`partOf` at the screen's `base` + the edit's offsets, then `replaceSelection`), rebases the panel's fix (`withoutFixEdit`) and, for the whole field, the check (`withoutEdit`), so no re-check fires and the next edit slides in; the panel closes after the last one. `writingEdit` keeps that input from closing it. Ignore is kept on `state.ignored` (by `original→replacement`) until another field is selected, so a re-check doesn't bring it back. Replace all applies the rest in one write (`apply`). Scrolling the field or the page moves the icon, underlines and whole-field panel with it (`moved`) instead of closing them (a hover-opened panel falls back to the icon); other screens still close on scroll. Single-line `<input>`s (search boxes, filters, form fields) are **never pre-checked**: they show the plain icon and the click sends the first request (the guard is in `scheduleCheck`), so focusing a search box costs nothing. Likewise, texts under 3 words (`hasEnoughWords`, `Intl.Segmenter` so CJK counts) get no automatic request anywhere, on the field icon, the selection icon or the menu opening; a click still asks. The selection menu reuses the same check for the selected text: its "Grammar fix" item (count, spinner, hidden when the check failed) opens the same panel (`field: false`, `base` = `offsetIn(selection)`), whose edits then land inside the selection only. Every typing pause is a guard call plus a `/check` call (rate limit).
- **Wrong keyboard layout** comes from the guard's 422 on that same check (`check.verdict`, also set by a 422 from `detect`, `translate`, `fix-grammar` or `rewrite` via `showVerdict`). A non-page selection is pre-checked too (300 ms after it settles; one request per selection), so both icons can warn: an orange `!` badge (`badge() === 'layout'`; orange `?` = random keystrokes (`gibberish`), orange N = grammar errors, green ✓ = clean, red `!` = the check failed). Clicking a mistyped text opens the layout card (`layout` screen) *instead of* the grammar panel or menu: the typed text struck through, `switchLayout` output, "Fix the characters" (F) which replaces locally and re-checks the fixed text, and ✕ which only closes — the API would refuse the text as typed, so there is no fallback. Random keystrokes open the `notText` notice instead, with nothing to press: every action stays off until the text changes (a gibberish verdict arriving while the menu is open replaces the menu). "Reads as" / the fix's `lang` come from `layoutLanguages()` in `core/layout.ts`, the same direction rule as `switchLayout`.
- **Voice input into a field**: the corner icon's hover pill has a mic (field icons only, never page text). `dictate()` keeps the caret offset (a textarea's `selectionEnd`, a contenteditable's `caretIn`) and shows the `recording` screen, focusing the field again (the pressed mic and Stop unmount, and focus on `<body>` makes Teams rebuild its composer); Stop or ↵ (`stopDictation`) transcribes. **The field is not written until Insert**: the selection becomes a page-kind stand-in holding the transcript (`State.dictation`: `transcript`, the working `text`, the caret `at`), so English opens the grammar panel on it (`fixDictation`, screen `grammar` with `dictated: true`: Replace / Ignore edit the panel's copy, Replace all takes every edit and inserts), and any other language opens the page-text menu (`translateInField` at once into the pair's target, else a pick). Both show the transcript collapsed (`panels/DictationBar.tsx`, a native `<details>`) and Insert / Copy; `insertDictation` writes the result at `at` (`replaceSelection` trims, so a needed space goes in with the previous character -- never after a `}`, which may close a mention token) and remembers a changed grammar result. `close()` on the `recording` screen sends `voice-cancel`, so Esc, blur and scroll release the mic.
- **Exceptions** (words kept as written: brands, names, terms, code). The selection menu offers "Add to Exceptions" when the selection is a word or short name (`isShortTerm` in `state.ts`: 1–4 words, ≤ 60 chars; never on a dictation). It opens the `exception` screen (`panels/ExceptionPanel.tsx`): the word prefilled with the trimmed selection, Kind (Brand / Name / Term / Code), Cancel back to the menu. Editing the word to another spelling saves the selection as a form it `replaces`, and on a field (not page text) offers "Fix it in this text too", which `replaceSelection`s it. `saveException` writes `vocabulary.addException` (`settings/vocabulary.ts`, key `local:vocabularyExceptions`, same term = replaced) -- **chrome.storage.local only, not the synced `Settings`**, like turned-off fields -- and the Settings page's Vocabulary → Exceptions tab lists, adds and removes the same entries live (`useVocabulary` watches the item). **The worker sends them**: before `translate` / `check` / `fix-grammar` / `rewrite` it attaches the exceptions whose term or a `replaces` form occurs in the text (`exceptionsIn` in `background.ts`; only those leave the browser). The API hides them from the model (`api/src/utils/exceptions.ts`: `mask` turns each whole-word hit into a `{{n}}` token numbered after the mentions, a wrong form taking its term's token; `restore` puts the term back). Grammar fix, check, rewrite and the guard mask every kind; `/fix-grammar` applies the model's edits to the masked text, drops any edit that adds or loses a token, unmasks, and only then diffs, so offsets stay in the request text and `jira` → `Jira` arrives as an ordinary edit. `/translate` masks Brand / Code only; Name / Term go to the prompt as a hint, so the sentence around them still inflects and a name may be transliterated. A cached check or fix isn't re-asked when an exception is added; the text has to change. The matcher is `findExceptions` in `shared/exceptions.ts` (exact term / `replaces` hits first, then any one word at least `SIMILAR` = 80% alike to a one-word term or form, case ignored, Levenshtein -- `typemeans` → `Typemeant`, decided in code, never by the model; the worker's `exceptionsIn` uses it too), shared by the API's `mask` and `GrammarPanel`: the panel (`GrammarView.exceptions`, fed by `settings/useExceptions.ts` in both the widget and the popup) puts a dotted green underline with a "From your exceptions · Kind" tooltip under each kept term in its preview, and labels an edit that only respells a wrong form (`exceptionOf`) "From your exceptions" with a green dot instead of "Grammar".
- A `generation` ref in `useTranslatorFlow` makes stale translation and detection responses get ignored after the widget closes.
- Opening the menu fires `detect` and fills the menu's "From:" line in place when it answers, so the panel is never rebuilt (and never jumps) under the cursor. The detected code is then sent as `sourceLang` on `translate`, which is what tells the API whether the detection was right. A failed detection is silent — it must not block translating — and `"und"` is treated as no detection at all. The target list is the popup's "Translate into" list (`intoLanguages` in `settings/history.ts`: the pinned languages, then the most used favorites up to 3 in all, then "Used lately" from the local history); the detected language is left out of it (`menuLanguages`). Once detection answers, the user's usual pair for that language (`pairTarget` over `topPairs(history)`: the most used pair starting from it, else one ending in it, flipped) is used. **Page text** is translated into its target at once (`translateInField`), into a translation field under the "detected" line (skeleton lines sized to the selection, then the text with Copy; state `translation`); the menu stays, and picking another language aborts the one in flight (`translate` takes an `id`, cancelled through the worker like `check`) and swaps the field. A **field's own text** is never translated unasked: the pair's target just sits under the "detected" line as shortcut `1`. The shown target is left out of "Translate to"; the digit shortcuts number what is shown (`menuShortcuts`). Only when detect 422s `mistyped` (or the check did) does the menu carry one more item below the languages: the selection re-typed on the other keyboard layout (`switchLayout`, no network). Clicking it replaces the selection and closes, with no translation, and the "From:" line reads "wrong keyboard layout". There is no UI yet for correcting it by hand.

**Testing notes**:
- Tests are colocated as `*.test.ts`. DOM tests opt into happy-dom with a `// @vitest-environment happy-dom` header, because the default environment is node.
- Because the widget's shadow root is closed, browser automation (Puppeteer) can't query it normally. Use CDP `DOM.getDocument({ pierce: true })` + `DOM.getBoxModel` to find and click its elements.
- **Voice input in a test browser**: launch Chromium with `--use-fake-ui-for-media-stream --use-fake-device-for-media-stream --use-file-for-fake-audio-capture=<file>.wav` (speech from macOS `say -o x.aiff "…"` + `afconvert -f WAVE -d LEI16@48000 -c 1`; append a few seconds of zeros to test the 3 s silence stop). The fake mic loops the file, so transcripts repeat. The browser never reaches OpenAI any more, so `--host-resolver-rules=MAP api.openai.com …` no longer forces the `/transcribe` fallback; it runs whenever the voice socket fails (a refused ticket, the API's provider session failing). Without `--use-fake-ui-…` the grant is missing and the `mic-blocked` path runs.
- **"It still behaves like before" after a rebuild**: first check which build Chrome runs. `npm run build` writes `extension/output/chrome-mv3`; `npm run dev` uses `output/chrome-mv3-dev`. The worker and the offscreen recorder only update on a reload in `chrome://extensions`, open tabs keep their old content script until refreshed. `grep` the built `background.js` for a string the change added to prove what a build contains.
- `GET /stats` reads the developer's real counts (`api/word-stats.json`): back the file up before a test that dictates or translates, and restore it after.
- **A bug tied to a specific field or element** (one site's editor, composer, widget): before fixing, ask the user for the element's markup and the site it comes from, unless they already gave both. Reproduce it in `playground/index.html` under the "Specific fields / elements" `<h2>`: an `<h5>` naming the site, then the markup trimmed to what reproduces the bug. Verify the fix on that playground element (`npm run dev:playground -w extension`), and keep it there as a regression case.
