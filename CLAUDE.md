# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

npm workspaces monorepo with two parts: `extension/` (Chrome MV3 frontend, WXT + TypeScript) and `api/` (Hono backend that owns translation, deployed as a single Supabase Edge Function), plus `shared/contract.ts` for the wire types both import. The user selects text in an input, textarea, or contenteditable field. A floating icon appears; clicking it opens a menu of favorite languages, and picking one replaces the selection with the translation fetched from the API.

**The extension is frontend only**: detect the selection, show the icon and menu, call `POST /translate`, and apply the result. It has no provider abstraction, provider choice, or provider config. Translation and provider selection live in the API (`api/src/resources/aiClient/requests/translate.ts`), because a provider key shipped in the extension is public.

## Commands

Root commands fan out to both workspaces (`npm test`, `npm run compile`, `npm run build`); `-w extension` / `-w api` targets one.

- `npm run db` (root): `supabase start` — local Postgres + edge runtime, needs Docker. Everything else assumes it is running.
- `npm run dev` (root): API + extension dev browser + playground together
- `npm run dev:playground -w extension`: extension + `playground/` on http://127.0.0.1:5555 (opened via `webExt.startUrls` in `extension/wxt.config.ts`); the manual test environment
- `npm run dev:api` (root): the **local Node server** on http://127.0.0.1:8787/functions/v1/, `node --watch`. Needs no Docker; env comes from Node's `--env-file-if-exists` (root `.env` then `supabase/functions/.env`), so there is no dotenv import-order rule.
- `npm run dev:api:edge` (root): `supabase functions serve` on http://127.0.0.1:54321/functions/v1/ — the real gateway and the real Deno runtime. **Run this before deploying**; it is the only local path that exercises them.
- `npm run token -w api`: mints a signed dev token for curl, so the Node server can be used with no Supabase stack running. Takes an optional user uuid. Deno runs the TS directly — no build step, so keep API code erasable: no enums, no parameter properties.
- `npx supabase migration new <name>`, then `npx supabase migration up` (local) / `npx supabase db push` (linked project). Files live in `supabase/migrations/`; don't edit applied ones.
- Deploy the API: `npx supabase link --project-ref <ref>`, `npx supabase secrets set --env-file supabase/functions/.env`, `npx supabase functions deploy api`.
- `npm run build`: production build into `extension/output/chrome-mv3`. Load it unpacked from `chrome://extensions`.
- `npm run compile`: type check. The extension needs the generated `.wxt/` types; run `npx wxt prepare` in `extension/` on a fresh checkout or after adding entrypoints.
- `npm test`: all unit tests (Vitest), both workspaces
- `npm run deploy`: compile + test + zip + `wxt submit` to the Chrome Web Store. Credentials live in the git-ignored `.env.submit`, created by `npx wxt submit init`. Bump `package.json` version first, because the manifest version comes from it. `npm run deploy:check` is a dry run.
- Single test file: `npx vitest run src/api.test.ts` from inside `extension/` or `api/`. Single test by name: `npx vitest run -t "surfaces the API error message"`.

There is no linter configured. `playground/index.html` has one of each field type.

## Architecture

`srcDir` is `src`, so WXT entrypoints live in `src/entrypoints/` (`background.ts`, `content.ts`, `options/`). Import WXT APIs explicitly from subpaths (`wxt/browser`, `wxt/utils/storage`, `wxt/utils/define-background`, …) instead of relying on auto-imports.

Extension layout:
- `src/api.ts` has `translate()` and `detect()`, the only `fetch`es to the API. The base URL comes from `WXT_API_URL`, falling back to `http://127.0.0.1:54321/functions/v1/api`, and its origin must be in `host_permissions` (`wxt.config.ts` lists the local stack and `https://<project-ref>.supabase.co`; keep the two in sync by hand). API error bodies become a plain `Error` carrying the API's message.
- `src/entrypoints/background.ts` handles messages and calls `translate()`. The page url is read from the `onMessage` `sender`, not the message body, so a compromised page can't forge it — that is why `handle()` takes the sender.
- `src/settings/` is a **cache**, not the source of truth: settings live on `profiles.settings` so they follow the user across devices. The content script reads the cache on every icon click (fast, works offline and signed-out); the options page and the sign-in handler go through the worker's `get-settings` / `save-settings`, which write the cache after the API answers. Saves are API first, cache second, so the server stays authoritative. Last write wins. An empty `favoriteLanguages` (the shared default) means "not chosen yet": `storageSettings.get()` fills it with `browserLanguages()` (`navigator.languages` → supported base codes, `en-US` → `en`; first = default target), since the server can't see the browser.
- `src/auth/` is the session and OAuth flow. `session.ts` is a **separate** storage item from `Settings`, because the options page's `update()` does a shallow spread that would clobber a nested session.
- `src/core/languages.ts` is the static language list.

**API** (`api/`): deployed as two Supabase Edge Functions (`api`, `health`); run locally as a Node server. It is layered — entrypoint → wiring (`app.ts`) → middleware → controller → AI request / repository → resource (`resources/db.ts`, `resources/aiClient/client.ts`), each layer calling only the one below it. **[`.claude/rules/api-architecture.md`](.claude/rules/api-architecture.md) is the source of truth for that split** (what each layer owns, what it must not do, the folder map, where new code goes); read it before adding a route, a guard, a provider call or a table. `index.ts` only calls `Deno.serve(app.fetch)`, so tests hit `app.request()` with no port. Error bodies are `{error:{message, code}}` and `src/api.ts` surfaces the message; keep the codes in sync with `shared/contract.ts`. `repositories/translations.ts` (`translationsRepository`, mapping app records to columns) saves every translation, failures included, to the Postgres table `translations` (created by `supabase/migrations/`); a row's id starts with the request's log id. A row also records `user_id` (FK to `auth.users`, `on delete set null`), `url` (the page the extension was used on), `model` (what the provider reports it used, not what was requested) and the provider's `input_tokens` / `output_tokens` / `total_tokens`; all nullable, since rows predating auth have no user, failures report no usage, and non-extension callers send no url. `trace_id` is a **generated** column (`sha256(text)` in hex, indexed), not written by the repository: it fingerprints the selected text so every attempt on it -- retries, other target languages -- groups under one id and the action can be repeated. There is **no RLS yet** — nothing reads this table from a client, and the function writes it over a connection that bypasses policies anyway.

`POST /detect` answers what language a selection is in, and whether it is a language at all: `mistyped` flags text typed with the wrong keyboard layout (`ghbdtn` for `привет`), in which case `lang` is `"und"` and the client re-types it locally with `switchLayout` (`src/core/layout.ts`) — a key-position map, so the fix costs nothing and can't hallucinate. It is asked when the in-page menu opens, before a target is picked, together with a `fix-grammar` of the selection (the menu's "Grammar fix" item shows its error count) — an icon click therefore costs three requests against the 60/min limit. `repositories/detections.ts` saves each attempt to `detections`, which mirrors `translations` column for column (id, usage, error, the generated `trace_id`), so a detection and the translations of the same text join on `trace_id` without a foreign key. Its one extra column, `verified`, is **written by `POST /translate`, never by the detection**: `null` = the menu was closed without translating, `true` = the user translated with the detected language, `false` = the user sent a different `sourceLang` and the detection was wrong. Only the user's latest detection of that exact text is marked, in a `waitUntil` that can't slow or fail the translation. `verify()` matches the row by hashing the text in SQL (`::text::bytea`, not `::bytea` — a bare cast types the bind parameter as bytea and Postgres would parse the string as escaped binary instead of hashing its characters), so the client carries nothing but the language.

`POST /fix-grammar` takes the same body as `/detect` (`{text, url?}`) and returns `{text, html, mistyped, gibberish}` with grammar, spelling and punctuation fixed in the same language — unchanged if nothing needed fixing. `mistyped` is `/detect`'s wrong-keyboard-layout flag, judged in the same call so the background check needs no second request; a mistyped text comes back unchanged. `gibberish` (never together with `mistyped`) flags random keystrokes that are no language on either layout (`adfasdf`) — returned unchanged too, so the extension doesn't show them as clean. Rate limited like the other provider routes. `repositories/corrections.ts` saves each attempt to `corrections`, which mirrors `translations` (id, usage, error, generated `trace_id`). No extension UI yet.

`POST /rewrite` takes `{text, url?, style}` with `style` one of `REWRITE_STYLES` (`natural` = how a native speaker would say it, same register; `formal` = official/business register) and returns `{text}` rewritten in the same language, errors fixed along the way. Same guards as `/fix-grammar`. `repositories/rewrites.ts` saves each attempt to `rewrites`, which mirrors `corrections` plus a `style` column. No extension UI yet.

`profiles` is the user record we own — `auth.users` belongs to GoTrue and must not gain application columns. The `on_auth_user_created` trigger (in `supabase/migrations/`) copies id/email/provider metadata across at sign-up; `repositories/profiles.ts` upserts anyway so a missing row still yields working settings. It holds `settings` as jsonb mirroring the extension's `Settings` object 1:1, merged over `DEFAULT_SETTINGS` on read so a new setting needs no data migration. Still no RLS — the API is the only reader. The save never fails a translation.

API rules:
- **Three entrypoints, one app.** `index.ts` (edge, `Deno.serve`), `health.ts` (edge, public probe) and `server.ts` (local Node) are the *only* places allowed to know which runtime they are on. `app.ts` must never branch on runtime — if something differs, it belongs in an entrypoint or in `dev/dev-gateway.ts`.
- `dev/dev-gateway.ts` **emulates** the Supabase gateway locally: the `/functions/v1/...` prefixes, the gateway's own 401 bodies (`{code, message}`, not the app's `{error:{...}}`), and a real signature check standing in for `verify_jwt`. It accepts both token kinds: **ES256/RS256 via the GoTrue JWKS endpoint** (how real sessions are actually signed — the local stack does *not* use the legacy shared secret) and **HS256** for tokens from `npm run token -w api`. **Dev-only auth bypass:** a request with *no* `Authorization` header is signed in as `DEV_USER_ID` (default `00000000-0000-4000-8000-000000000000`, seeded into `auth.users` by `supabase/seed.sql` on `db reset`), so the extension works signed out against the Node server; a token that *is* sent is still verified. `dev:api:edge` and production stay gated. It is an emulation and can drift — that is why `npm run dev:api:edge` before deploying is a rule, not a suggestion.
- `api/src/**` deliberately stays outside `supabase/functions/`. `[functions.api]` / `[functions.health]` in `supabase/config.toml` point `entrypoint`/`import_map` at it (paths resolve from `supabase/`), which keeps the npm workspace layout for vitest and `tsc`. Don't move the sources. `api/dev/` holds local-only code (`dev-gateway.ts`, `dev-jwt.ts`, `dev-token.ts`) and is never deployed.
- `app` is built with `basePath('/api')` because Supabase strips `/functions/v1` and hands the app paths starting with the function name. The basePath and the function name must match; tests request `/api/translate`.
- Read config through `env()` in `env.ts` (Deno.env when deployed, `process.env` under vitest), never `process.env` directly. Supabase has secrets at module load, so module-level reads are fine.
- The DB save is wrapped in `waitUntil()` (`EdgeRuntime.waitUntil`), which keeps the isolate alive until the insert lands. Without it the row is lost the moment the response returns. It is a no-op under vitest.
- Runtime deps are declared in `api/deno.json` (Edge Functions have no `package.json` support); the same packages sit in `api/package.json` `devDependencies` only so vitest and `tsc` resolve them. Bump both together.
- Secrets live in git-ignored `supabase/functions/.env` (template: `.env.example` beside it), loaded by `supabase start` / `--env-file` and pushed with `supabase secrets set --env-file`.
- **Two functions, because `verify_jwt` is per-function and the gateway enforces it before the handler runs.** `api` has `verify_jwt = true` (signed-in users only); `health` has `verify_jwt = false` so uptime probes stay anonymous. That is the only reason `health.ts` is a separate entrypoint rather than a route on `app.ts`.
- `userIdFrom()` in `middleware/auth.ts` **decodes but does not verify** the JWT — the gateway already checked the signature and rejects the publishable key. Setting `verify_jwt = false` without adding signature verification would make `sub` forgeable. The two are coupled; the comment at the call site says so.
- A 401 can come from the gateway *before* the handler, with a different body (`{code, message}`, no `error` wrapper). `extension/src/api.ts` therefore derives `unauthenticated` from the **status**, not the body, or a signed-out user gets a generic error instead of the sign-in prompt.
- OAuth is hand-rolled PKCE in `extension/src/auth/oauth.ts` (`chrome.identity.launchWebAuthFlow` + two fetches), so the extension still has zero runtime dependencies. `apikey` goes in the **query string** on `/auth/v1/authorize` because a navigation carries no headers. Tokens refresh **on demand, never on a timer** — an MV3 worker is killed between requests.
- Adding an OAuth provider = a `[auth.external.<name>]` block in `supabase/config.toml` plus an entry in `extension/src/auth/providers.ts`. Nothing else.
- Two env files: git-ignored **`.env` at the repo root** holds provider ids/secrets that the CLI substitutes into `config.toml` at `supabase start`; **`supabase/functions/.env`** holds function runtime secrets. Don't merge them.
- No `DATABASE_URL` in production — Supabase injects `SUPABASE_DB_URL`; `resources/db.ts` prefers `DATABASE_URL` as an override. postgres.js runs `max: 1, prepare: false` because each isolate gets its own pool.
- `app.test.ts` mocks the AI requests (`resources/aiClient/requests/*`), `resources/db.ts` and the repositories, so API tests need no key, DB or network. Mock any new module that opens a connection when it loads — `resources/aiClient/client.ts` throws without `OPENAI_API_KEY`, so a stale mock path fails the whole file on load.
- `GET /health` returns 503 only when a DB URL is set and `select 1` fails (5 s connect timeout); `db: "disabled"` is still 200.

**Runtime flow**: The content script and the options page talk to the background worker only through the typed protocol in `src/messaging/messages.ts` (`translate`, `detect`, `open-options`, `sign-in`, `sign-out`, `get-account`, `get-settings`, `save-settings`). Sign-in must run in the worker: `chrome.identity` is unavailable to content scripts and the options page. Responses are `{ ok, data } | { ok: false, error }`, because `Error` objects don't survive messaging. When adding a message type, update both `Message` and `ResponseMap`. The API call must stay in the background worker: `host_permissions` exempt it from page CORS, and on HTTPS pages a content-script fetch to an `http://` API would be blocked as mixed content.

**Toolbar popup** (`src/entrypoints/popup/`): the toolbar icon opens it (WXT adds `default_popup`; the old `action.onClicked` → options page is gone, settings are the popup's sliders icon). `main.tsx` is the container, `Popup.tsx` presentational (Home, Languages picker, History; stories beside it). It translates typed text through the same `detect` / `translate` messages (debounced detect; "Try another" re-asks and keeps versions in memory only). The worker records `sender.url`, which for the popup is its own `chrome-extension://` page, not the tab. History is **local only**: `settings/history.ts` (`historyStore`, key `local:popupHistory` kept from when it was popup-only; the last 200 entries; no age-based pruning, by choice). It takes popup translations, in-page widget translations (recorded by `Translator.tsx` once applied or shown) and **applied** grammar fixes and rewrites (`kind: 'grammar'`, on Replace or Copy, never for background checks); no `kind` = a translation. Each card and the Recent row start with a translate / grammar icon; a grammar entry's chip reads "Grammar", it never offers "Translate this again", and opening it puts the fixed text into the input. "Used lately" (per side: sources in the from-picker, targets in the into-picker), the History filter tabs (`topPairs`) and the day groups (`byDay`) derive from it. The Home pair defaults to `defaultPair` (the most used history pair, else the first two favorites); detection `orient`s it (typing the target language flips it, any other language becomes the source), and only a picked or detected source is sent as `sourceLang`. Once history has two pairs they show as chips above the selects. Thumbs up/down are stored on the entry (`rating`) and never sent: there is no feedback endpoint. Delete / Clear all keep the previous list in memory for a single footer Undo, dropped on leaving History. A thumbs-down card swaps Copy for "Translate this again", which opens the entry on Home and appends a new version. The header switch edits `Settings.disabledSites` for the active tab's host (`activeTab` permission gives the popup its url). **Insert** goes popup → `tabs.sendMessage(tabId, {type:'insert'})` → the content script's `insertIntoFocusedField` (`content/insert.ts`, caret or selection of the page's focused field, then `replaceSelection`). It is not a worker message, and only the frame holding the field answers, so an undefined answer means "no field focused".

**Content script** (`src/entrypoints/content.ts` + `src/content/`):
- `selection.ts` snapshots the selection when the icon appears: offsets for text controls, a cloned `Range` for contenteditable. Before replacing, it checks with `isSelectionUnchanged` that the text wasn't edited during translation. Only `text`/`search` inputs and textareas count, and `isTextControl` also drops login/contact/payment inputs via `isExcludedField` (autocomplete tokens, `inputmode`, `spellcheck="false"`, and `name`/`id`/`aria-label` matching login/user/email/otp/card/phone…; name rules apply to `<input>` only, since a textarea is prose). A page opts out with `data-ai-translator="off"` (or Grammarly's `data-gramm="false"`) on the field or any ancestor, contenteditable and page text included.
- **Turned-off fields**: hovering a field's icon (corner or in-field selection, never page text) opens a pill with "Turn off in this field". It stores `{site, key: fieldKey(el), label}` in `settings/disabled-fields.ts` — **chrome.storage.local only, deliberately not in the synced `Settings`**. `fieldKey` prefers `data-tid`/`name`/`aria-label`/`placeholder` and strips uuid/digit runs from ids, so Teams' per-load `new-message-<uuid>` still matches. `Translator.tsx` mirrors it in an `offFields` ref (same pattern as `siteDisabled`); the options page lists them with "Turn back on".
- **Disabled sites**: `Settings.disabledSites` (hostnames, validated by `HOSTNAME` in `shared/contract.ts`) turns the whole widget off on a site and its subdomains (`isSiteDisabled` in `core/sites.ts`). `Translator.tsx` keeps it in a ref fed by `storageSettings.watch`, so an options-page save applies to open tabs without a reload. The options page takes one hostname per line; `parseSites` reduces pasted urls to hostnames. `PUT /settings` replaces the whole jsonb, so every save sends the full `Settings`.
- `replace.ts`, for contenteditable: first dispatches a synthetic `paste` event. Model-based editors (CKEditor, Lexical, ProseMirror; e.g. Teams) revert direct DOM edits, `execCommand` included, but they handle paste and cancel it, and a cancelled paste means done. Otherwise, and for inputs and textareas, it uses `document.execCommand('insertText')`, which preserves native undo and is picked up by React-style frameworks. It falls back to `setRangeText` or `Range` edits plus a synthetic `input` event. If `execCommand` returns true, trust it; don't re-apply the edit.
- `entrypoints/content.ts` only calls `mountTranslator()`. `ui/translator-widget.ts` builds the **closed** shadow root on a fixed-position host and renders `ui/Translator.tsx`, which owns the whole flow (document listeners, detect, translate, sign-in, layout fix). Its state is the pure reducer in `ui/translator-state.ts`; `ui/TranslatorWidget.tsx` is presentational only (what Storybook renders). `preventDefault` on `mousedown` inside the widget keeps focus and the selection in the page's field, so don't remove it.
- Two flows share the widget. A selection gets the icon above it → language menu → translate. A focused field with nothing selected gets an icon in its bottom-right corner (`getFocusedField` / `wholeField` in `selection.ts`, a snapshot of the whole field) → `fix-grammar` → the grammar panel, whose Replace / N / O rewrite the whole field. The field is re-read from its element at click time, not from focus: pressing a HeroUI button moves focus into the widget, which is also why `focusout` ignores `relatedTarget === host`.
- A third flow covers page text outside any field: `getPageSelection` in `selection.ts` returns `kind: 'page'` (tried after `getEditableSelection`, before the focused field). It gets the same icon → menu with detection, but translate only (`readOnly` hides Grammar fix and the layout item, and no `fix-grammar` is asked). The translation opens the `translated` panel with Copy, because page text is never replaced. `replaceSelection` takes `WritableSelection`, so the compiler keeps page selections out of it.
- The focused-field icon is pre-checked: focusing a field, and each `input` or `beforeinput` (debounced 500 ms; CKEditor/ProseMirror/Lexical cancel `beforeinput` and never fire `input`), runs `fix-grammar` in the background. While in flight the icon shows a centered spinner (`isChecking()`), then the `span.fix` count (orange) or a green check (`badge()`, only while the checked text still matches the field). Clicking opens the grammar panel from that result; mid-flight, it awaits the same request (`pendingCheck`). Only a never-checked text makes the click ask. Single-line `<input>`s (search boxes, filters, form fields) are **never pre-checked**: they show the plain icon and the click sends the first request (the guard is in `scheduleCheck`), so focusing a search box costs nothing. Likewise, texts under 3 words (`hasEnoughWords`, `Intl.Segmenter` so CJK counts) get no automatic request anywhere, on the field icon, the selection icon or the menu opening; a click still asks. The selection menu reuses the same check for the selected text: its "Grammar fix" item (count, spinner, hidden when the check failed) opens the same panel, whose Replace then replaces only the selection. Every typing pause is one provider call (rate limit, a `corrections` row).
- **Wrong keyboard layout** comes from that same check (`fix.mistyped`). A non-page selection is pre-checked too (300 ms after it settles; one request per selection), so both icons can warn: an orange `!` badge (`badge() === 'layout'`; orange `?` = random keystrokes (`gibberish`), orange N = grammar errors, green ✓ = clean, red `!` = the check failed). Clicking a mistyped text opens the layout card (`layout` screen) *instead of* the grammar panel or menu: the typed text struck through, `switchLayout` output, "Fix the characters" (F) which replaces locally and re-checks the fixed text, and ✕ which marks the check `dismissed` (the `dismissWarning` action) (no `!` for that text again) and falls back to the regular widget. Random keystrokes open the `notText` notice instead; its "Check anyway" dismisses the same way. "Reads as" / the fix's `lang` come from `layoutLanguages()` in `core/layout.ts`, the same direction rule as `switchLayout`.
- A `generation` ref in `Translator.tsx` makes stale translation and detection responses get ignored after the widget closes.
- Opening the menu fires `detect` and fills the menu's "From:" line in place when it answers, so the panel is never rebuilt (and never jumps) under the cursor. The detected code is then sent as `sourceLang` on `translate`, which is what tells the API whether the detection was right. A failed detection is silent — it must not block translating — and `"und"` is treated as no detection at all. The detected language is left out of the target list (`menuLanguages`), and the digit shortcuts number what is shown. Only when detect answers `mistyped` does the menu carry one more item below the languages: the selection re-typed on the other keyboard layout (`switchLayout`, no network). Clicking it replaces the selection and closes, with no translation, and the "From:" line reads "wrong keyboard layout". There is no UI yet for correcting it by hand.

**Testing notes**:
- Tests are colocated as `*.test.ts`. DOM tests opt into happy-dom with a `// @vitest-environment happy-dom` header, because the default environment is node.
- Because the widget's shadow root is closed, browser automation (Puppeteer) can't query it normally. Use CDP `DOM.getDocument({ pierce: true })` + `DOM.getBoxModel` to find and click its elements.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
